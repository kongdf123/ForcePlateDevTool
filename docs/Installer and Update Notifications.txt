## 1. Generate a Windows installer using Inno Setup

Create `installer/ForcePlateDevTool.iss`.

Requirements:

1. Package the output from the existing self-contained .NET publish directory: `artifacts/publish/`.
2. Generate an installer named `ForcePlateDevTool-Setup-v{version}.exe`.
3. Support both installation modes:
   - Per-user installation without administrator rights.
   - All-users installation with administrator authorization.
4. Use Inno Setup installation-mode overrides and an appropriate automatic Program Files/user Programs directory constant.
5. Create a Start Menu shortcut and offer an optional desktop shortcut.
6. Offer to launch the application after installation.
7. Register an uninstaller.
8. Preserve the same Inno Setup `AppId` across releases.
9. Configure x64 installation appropriately.
10. Ensure upgrading from an earlier installed version does not delete user settings or logs.

Recommended installation paths:

- Per-user: `%LOCALAPPDATA%\Programs\ForcePlateDevTool`
- All-users: `%ProgramFiles%\ForcePlateDevTool`

Recommended Inno Setup settings:

- `PrivilegesRequired=admin`
- `PrivilegesRequiredOverridesAllowed=dialog`
- `DefaultDirName={autopf}\ForcePlateDevTool`
- `ArchitecturesInstallIn64BitMode=x64`

Use a stable application ID, for example:

`{{A2C5D5C1-6A41-4B91-A8D2-5A62A1F79E10}`

Use Inno Setup preprocessor definitions to pass the release version from the workflow. Do not hard-code the production version in the installer script.

## 3. Add an update-checking service

Create a small, testable service, such as `Services/UpdateService.cs`. Adapt its namespace and location to the existing project structure.

The GitHub repository is currently public. Use the unauthenticated GitHub Releases API:

`https://api.github.com/repos/kongdf123/ForcePlateDevTool/releases/latest`

Use `HttpClient` with a reasonable timeout and appropriate error handling.

Retrieve at least:

- `tag_name`
- `html_url`
- `body`
- `prerelease`
- `draft`
- Installer asset download URL, when present

Behavior:

1. Ignore draft and prerelease versions.
2. Parse stable semantic versions correctly, including the leading `v` in release tags.
3. Compare the latest release version with the installed application version.
4. Prefer the matching `ForcePlateDevTool-Setup-v{version}.exe` asset.
5. If the installer asset is missing, offer to open the GitHub release page instead.
6. Never embed a personal access token or other secret in the application.
7. Handle offline, timeout, rate-limit, malformed-response, and server-error conditions gracefully.
8. A failed update check must never prevent the application from starting or connecting to hardware.
9. Make the service unit-testable, with the HTTP dependency injectable.

Determine the installed version from the assembly metadata already set by the release workflow. Handle development builds such as `0.1.0-dev` explicitly so they are not incorrectly treated as production releases.

## 4. Add WPF update notifications

Integrate the update service into the existing WPF UI without blocking application startup.

Required UI:

- Display the installed version in an appropriate About or Settings area.
- Add a `Check for Updates` command under Help or an existing equivalent menu.
- Show a non-modal notification when a newer stable version is available.
- Display the installed version, latest version, release notes, and a `Download Update` action.
- Provide `Remind Me Later` or `Dismiss`.
- Open the official GitHub release or installer asset using the operating system's default browser.
- Do not download and install updates silently.
- Do not restart the application automatically.
- Do not interrupt an active measurement or force-plate acquisition workflow.

Automatic checks should run asynchronously after startup. Check at most once per application session initially; optionally support a 24-hour interval later.

Persist a dismissed-version value using an existing suitable settings mechanism, or a per-user settings file under `%LOCALAPPDATA%`. Do not write user settings into `Program Files` or the installation directory.

A failed network request should be logged appropriately without showing a disruptive error dialog during startup.
